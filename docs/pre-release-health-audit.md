# First-release code health audit

Reviewed on 2026-10-20–22 from `develop` at `5652729`. The checkout was clean and matched `origin/develop` after fetch before edits. The audit changes are recorded on `develop`; no existing local changes were overwritten.

The implemented Android features now have a stronger persistence and failure-handling baseline for release preparation. This is not a claim of complete release certification: physical-device acceptance and the separately requested release configuration stage remain outstanding.

## Necessary corrections

| Problem | Correction and evidence |
| --- | --- |
| Tasks and their groups lived in separate databases. Clearing references and deleting a group could partially complete, and SQLite could not enforce the relationship. | Both tables now live in `task.db`. `groupId` is nullable in storage, has an index and a `SET NULL` foreign key. Domain/UI `0` still means no group. Deleting a group keeps tasks, timestamps and attachments; real Room tests verify this. |
| Notes and passwords had no database-enforced parent relationships. | Notes use an indexed `SET NULL` foreign key; passwords use indexed `RESTRICT`, with the existing transaction moving credentials before service deletion. Tests verify rejected invalid references, rollback on invalid replacement and unchanged ciphertext/key/nonce. |
| A form could save a group deleted since the form was opened. | Task/note DAOs resolve the group inside the same transaction as the upsert. A missing group becomes ungrouped. |
| Room upsert returns `-1` on updates; task/group repository callers could receive that sentinel as an ID. | Repository-facing writes return the existing ID for edits and the generated ID for inserts. Task IDs are non-null in the entity; new rows use `0` for auto-generation. |
| The old DAO priority query treated an empty priority list as matching nothing. | Empty priority selections now mean no restriction, consistently with the domain/UI filter. Instrumented tests cover status and priority combinations. |
| Task form observation stopped completely when the group flow failed. There was no retry for failed task/list loads. | Errors are handled inside source flows; form state continues updating. Retry resubscribes without discarding the draft and reloads a previously failed task. Regression tests verify draft preservation and recovery. |
| Task form group resolution used possibly unavailable UI state. | Save resolves the group through the repository, with a transactional DAO check as the final guard. |
| Saving a stale task form could undo completion performed from a notification and re-arm the reminder. | Form saves preserve the latest stored completion value under the shared mutation lock. A regression test verifies that title edits still save without undoing completion or scheduling the completed task. |
| An open form could recreate a task that had been deleted. | Saving an existing task requires that it still exists before importing images. Regression test verifies no write/import on failure. |
| Cancelling completion/deletion could split database changes from attachment/alarm side effects; alarm cancellation could prevent task deletion. | Once a write starts, task completion/deletion and note deletion finish their side effects in a non-cancellable section. Task deletion commits and cleans attachments before alarm work; receivers already reject deleted rows. Scheduling failures remain visible to callers. |
| Concurrent note save/delete could clean an outdated attachment set or recreate the deleted note. | A shared mutation mutex serializes note writes, reads for mutation and cleanup. Controlled coroutine tests cover concurrency and cancellation at the delete boundary. |
| DataStore read failures reached the app theme/language collectors as uncaught failures. | Appearance consumers retain their last value (defaults only before the first read), retry reads and preserve cancellation. Raw settings/notification reads still propagate errors; fallback values are never persisted. |
| Password lists/Home loaded encrypted payloads and wrapped keys for every row despite using only metadata. | A Room projection reads only public metadata, with service lookup indexed in memory. Single-record decryption/authentication behavior is unchanged. |
| FCM registration tokens and notification titles were printed in logs; foreground notification posting lacked a permission guard. | Token/content values are no longer logged. Foreground posting checks permission and handles concurrent revocation. |

## Room version-1 contract

All three databases explicitly export schema version **1** through the existing Room Gradle plugin (`composeApp/schemas`). These JSON files were generated by Room, not edited by hand:

| Database | Tables | Referential action |
| --- | --- | --- |
| `TaskDatabase` / `task.db` | `TaskEntity`, `task_groups` | Deleting a group sets task `groupId` to SQL `NULL`. |
| `NoteDatabase` / `note.db` | `notes`, `note_groups` | Deleting a group sets note `groupId` to SQL `NULL`. |
| `PasswordDatabase` / private `passwords.db` | `passwords`, `password_services` | Deleting a referenced service is rejected until records are reassigned. |

Parent IDs are primary keys. Child references are indexed; notes also index their existing `updatedAt` ordering. Password service `nameKey` keeps its unique index. Group name checks run in transactions; the concurrent duplicate-creation test confirms only one insert commits. Defaults run only in `onCreate` and deleted defaults do not return when the database reopens.

Task Room uses the bundled SQLite driver on Android as well as iOS, like the other databases. This follows the [Room KMP driver guidance](https://developer.android.com/kotlin/multiplatform/room#select-a-sqlite-driver); existing Room/runtime versions were retained.

The separate task-group database wiring and historical development-only task/note migrations and version-2 exports were removed. There are no newly authored migrations and no destructive fallback. No installed database or user data was cleared. Old development installations may fail the schema/version check and are **not** an upgrade path to this new baseline; use a separate disposable test installation, preserving any important development data first. An instrumented test confirms that opening an unsupported development database fails while its original contents remain intact.

Once version 1 ships, retain these schema files unchanged. For an actual later schema change, increment that database's version, export the new schema, implement the real migration path on both platforms and test upgrading populated databases as well as fresh creation. Preserve IDs, content, attachment references, timestamps and encrypted records. Do not reuse the pre-release reset policy after distribution. No hypothetical future migration has been implemented here.

## Optional maintainability and scale improvements

- Home's `domain` package still imports Compose and presentation report types; legacy core validation also depends on presentation. Move rendering composition to presentation and separate report models during a focused cleanup. No broad package rewrite was needed for the corrections above.
- Lists and Home reports still observe complete task/note collections and perform filtering/reporting in memory. Benchmark representative large datasets before introducing SQL aggregate/projection queries or pagination.
- Consider lifecycle-owned dependency injection for the app language scope and a more gradual retry interval for prolonged storage failure; current retries keep the app usable without altering stored settings.
- Lint's newer-dependency/KTX suggestions, AndroidX ExifInterface replacement, orientation adaptation and icon-shape guidance are separate improvements. Dependency upgrades should be deliberate and tested across Android/iOS.
- Lint also flags target API, app-bundle language behavior and backup/transfer declarations. Record these for the next release-preparation stage requested by the owner; they were not changed or certified here.

The source/persistence baseline is suitable to move into that next stage. Final release approval should follow the remaining device acceptance checks and the separately scoped release work.
